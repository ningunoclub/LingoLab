## Goal

Port the two pages where a teacher reads a saved game: the list of saved results (`/results`) and the detail
view of one game (`/results/[result_id]`) with an Overview, a Players and a Questions tab. Until then `/results`
was a "coming soon" placeholder, although the dashboard already linked to it. Bruno's instruction was one line:
"can we get started on PR 10?" The scope came from the Phase 2 breakdown in `MIGRATION.md`.

## What happened

1. **Inventory.** Claude read the eight legacy files under `frontend/src/routes/results/` (562 lines in total).
   They import nothing from `$lib` besides i18n and the question types. The total is above the skill's
   ~400-line threshold for proposing a split, but `MIGRATION.md` already planned the two routes as one PR, so no
   split was proposed. The inventory became the body of PR #29.
2. **Checking the backend response.** The generated API types leave `answers`, `player_scores` and `questions`
   as `unknown`, and the backend model declares `answers` as a flat list while the save helper
   (`socket_server/export_helpers.py`) writes one list per question. The dev database held no saved results.
   Claude therefore ran a short script inside the api container: it inserted a temporary result for an
   existing quiz, called the real FastAPI endpoints in-process with the sign-in dependency overridden, and
   deleted the row again. The first version of the script failed on a wrong field name (`Quiz.user` instead of
   `user_id`). The second showed that the endpoints work, that `answers` arrives as one list per question, that
   scores arrive as **strings**, and that an unknown id returns 404 and a malformed one 422. No backend change was
   needed. A sign-in through the web app was not attempted, because an earlier session had been blocked from
   signing in the dev account automatically.
3. **Findings that shaped the port** (all logged in `MIGRATION.md`):
   - Neither legacy route checked the sign-in. Signed out, the list said "No results saved so far" and the
     detail page crashed; a failed request on the list also looked like an empty list.
   - Both legacy loads add `?include_quiz=true`, a parameter the backend does not have.
   - A multi-select (CHECK) answer is stored as the positions of the ticked answers (for example `"02"`), and
     legacy printed that string as the player's answer.
   - Slides were listed as questions with "Average score: NaN", and opening one treated the slide's canvas data
     as a list of answers. Averages also printed "NaN" when nobody had played or answered.
   - The quiz title was inserted as raw HTML, including inside the overview sentence, which is itself raw HTML.
   - The key for "n correct answers" uses the plural format of an older i18next version. The version used in
     `web/` (26) ignores it, so the page would have said "2 correct answer".
4. **Implementation** (by Claude), in `web/src/features/results/` unless noted:
   - `resultsApi.ts` fetches both endpoints and turns the response into typed data: scores become numbers,
     every question gets an answer list (empty when none was stored), and 404/422 become a "not found" error.
   - `resultStats.ts` holds legacy's sums and counts as pure functions (averages, ranking, correct answers per
     player, answer counts per option, CHECK answers as text).
   - Pages: `ResultsListPage.tsx`, `ResultPage.tsx` (tabs, back link, loading, error and not-found states),
     `GeneralOverview.tsx`, `PlayerOverview.tsx`, `QuestionOverview.tsx` and `QuestionDetails.tsx`. Question
     text goes through the shared `RichText` component, as planned since PR #19.
   - Routes: the placeholder `routes/results.tsx` was replaced by `routes/results/index.tsx` and
     `routes/results/$resultId.tsx`, both with the existing `requireAuth` guard.
   - New UI component: shadcn `Tabs` (built on `radix-ui`, already a dependency). The shadcn CLI again wrote
     `import { cn } from "cn"`, the known quirk noted in the handoff memory; Claude corrected it.
   - One change outside the route: `choiceAnswers()` in `features/host/gameQuiz.ts` now takes only a question's
     answers, so the results page could reuse it. Its behaviour did not change.
   - i18n: the plural key was renamed to `correct_answer_one` / `correct_answer_other`; seven other new keys
     (en + de) cover the states legacy did not have (load error, not found, back link, "nobody answered") and
     screen-reader labels. The German overview sentence gained the bold markup the English one already had.
5. **Tests.** 24 new unit and component tests against a fixture shaped like the real response
   (`web/tests/fixtures/game-result.json`). One test checks that a title containing HTML stays plain text in the
   overview sentence; it passed on the first run. A new e2e test (`tests/e2e/results.spec.ts`) covers list →
   detail → tabs → back, the empty list, an unknown id and the sign-in redirect. Its first run failed because
   of a wrong Playwright call (`route.url()` instead of `route.request().url()`).
6. **Visual check and two layout fixes.** As in PR #28, Claude took screenshots through a temporary Playwright

   below are from after all three fixes.
7. **A file from outside this task.** The full `pnpm lint` failed on `web/tests/e2e/zz-shots.spec.ts`, an
   untracked screenshot script for the player loop created at 09:49 the same day. It was not written in this

## Observations for the thesis

- **The type definitions did not describe the data.** The generated API types said `unknown`, and the backend
  model described a different shape from the one actually stored. Running the real endpoint once, with a
  throwaway row, settled the question before any UI was written. Without it, the parsing would have followed
  the model's declared shape, which the save helper does not write.
- **Small display bugs as a pattern.** Most findings in this route were not broken features but values a
  teacher could not read: "NaN", "02" as an answer, "2 correct answer". Each one needed a small judgement of
  what legacy *meant* to show. As in PR 8, these judgements were made by Claude and logged, not decided by
  Bruno beforehand. TODO(Bruno): whether such display fixes count as "behaviour changes" under the parity rule.
- **Screenshots found what the tests did not.** All tests passed while the phone layout cut off columns. The
  problems were found only by looking at the screenshots, and the second round found one that the first fix
  had missed.
- **Parallel work in one working tree.** A file from another session (the PR 9 screenshot script) sat in the
  working tree and broke the lint run. Committing only named files kept it out of this PR, but the full lint
  stays red until someone removes it.
